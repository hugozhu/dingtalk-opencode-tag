# 我们如何用一个 Harness 模板，把钉钉数字员工的交付成本打到最低

> 从生产环境打磨 4.1+ 版本的 `dingtalk-opencode-agent` 中，提炼出 13 个可复用最佳实践，做成数字员工项目的 harness 模板——新项目几分钟上线，起步成本为 0。

## 一、数字员工是什么，难在哪

「数字员工」本质是一个**企业里的钉钉账号**：它在群里/私聊里收消息，用 LLM 理解并生成回复，再以这个账号的身份发回去。听起来就是一个「群消息监听 → LLM 生成 → 发回群」的循环。

但真要从零做生产级交付，脏活全在循环之外：

- 进程挂了谁来拉起？拉起了但「大脑」和模型网关失联了怎么办？
- 断线重连、SSE 事件流退避、日志轮转、跨行消息解析
- 图片/文件/合并转发这些富媒体，怎么受控地下载、识别、注入上下文
- 多轮对话的会话怎么复用才不串上下文
- 上游框架天天在变，你的定制代码怎么还能干净 merge

这个 harness 模板把上述所有坑封装好了：**你只填几个配置就能上线，想定制业务再写自己的能力插件。**

## 二、分工哲学：opencode 负责「想和做」，harness 负责「人怎么跟它协同」

数字员工的「推理 + 任务执行」这件重活，交给更完备的 opencode——它有模型生态、工具调用、会话管理、权限控制一整套。本项目**只做「人机协同」那一层的最佳实践**：

- 钉钉侧的消息收发（dws CLI）
- 富媒体受控处理：图片识别 / 文件解读 / 合并转发
- Question 人在回路作答、群消息聚合
- 进程守护与自愈

分工清晰，能力可组装、可选配，按业务需要一个个交付。

而且整条链路**零成本起步**：默认跑 opencode 免费模型做文本对话，图片识别可选免费多模态模型或外部 gemini（质量更好）。

## 三、三层目录架构：改得动，也 merge 得回

FDE（交付工程师）最大的痛点是：改了一堆业务代码后，上游的修复再也合不进来了。我们用物理分层解决：

| 层 | 路径 | 能改吗 | merge 回 upstream |
|----|------|:---:|:---:|
| core | `src/core/` `bin/core/` `tests/core/` | ❌ 不要改 | ✅ bug fix 走 PR |
| custom | `src/custom/` `bin/custom/` `tests/custom/` | ✅ 在这里改 | ❌ 业务特定 |
| templates | `src/templates/` | ❌ 纯净参考 | FDE 的 diff 基线 |
| config | `config/*.local.*` | ✅ 填真实凭据 | ❌ gitignored |

core 只认注册表：能力是插件，声明式注册即生效；生成/发送走 core 定义的协议 + 注册点，custom 注入钉钉实现。**换 IM 平台，只需替换 custom 层的发送实现。**

加一个新能力就几行：

```python
register(Capability(name="my_cap", on_inbound=on_inbound,
                    handles_kinds={KIND_TEXT}, priority=50,
                    dedup=True, loop_guard=True))
```

msgId 去重、防自问自答由 core 统一处理，零样板。

## 四、生产级守护：几个最有意思的实践

**1. 进程活着 + HTTP 200 ≠ 大脑活着**

2026-08-08 出过一次事故：大脑与模型网关失联 16 分钟，期间进程存活检查、HTTP /session 探测全部正常，healthcheck 每 5 分钟报「健康」，但任何请求都答不出来——最后只能靠人在钉钉里发现。

于是有了检查 7 `check_brain`：按日志里「距上次检查以来」新增的失败条数，超过阈值才触发**一次真实模型调用**自检。健康时零请求零成本，失联时第一时间报警。

**2. 会话复用只按 conversation 粒度**

一个工作目录下会有上百个 session，「最近活跃的那个」未必属于当前这场对话——按目录复用会串上下文。复用逻辑统一按 `conv_id`（钉钉 openConversationId）：TTL 过期 + LRU 逐出，单会话串行、不同会话并行；复用的 sid 404 或回空时自动重建重试。所有能力（文本/图片/文件/合并转发）共用这套，所以**转发完再追问能接上上下文**。

**3. 守护循环 + 熔断**

`monitor.sh` 由 launchd/systemd 托管：`KeepAlive={SuccessfulExit:false}` 让崩溃自动拉起、主动退出等人工；连续 N 次健康检查失败触发熔断——发告警 + exit 0，不再无脑重启轰炸。

**4. 那些隐蔽到极致的坑**

- **上游输出格式随版本变**：事件格式有嵌套/扁平两种，格式不匹配时 bridge 把每条事件都静默跳过——进程活着、连接正常、健康检查全绿，但数字员工完全不响应。我们在 bridge 里内置格式健康检查：收到 ≥3 条原始事件却解析 0 条就告警。
- **`for line in sys.stdin` 有 readahead 缓冲**：低频事件流会卡在缓冲里不实时，改用 `iter(sys.stdin.readline, "")` 逐行读。
- **杀进程要连子树一起杀**：事件订阅会派生真正持连接的子进程，只杀父进程会把子进程甩成孤儿继续占着订阅，重启后新旧进程抢投递，表象是「收不到消息」。
- **远程重启必须用干净环境**：`/reboot` 由老进程派生、继承了旧 env，直接透传会让新配置不生效——用 `env -i` 跑重启，让 config 成为环境变量的唯一来源。

## 五、功能 100% AI Coding

代码库刻意做成「给 AI 写代码」友好的形态：物理分层、插件契约清晰、每个能力自带单测、边界写进 AGENTS.md。本项目的所有功能都由 AI 编码完成——**人给方向和验收，AI 探查、实现、真实链路验证、提 PR**。

要加能力？把需求一句话丢给 Coding Agent，它照着现有插件范式就能写，还会自己补单测、跑验证。

## 六、三步上线

1. **装工具 + 授权**：`curl -fsSL https://opencode.ai/install | bash` 装 opencode，装 dws CLI，钉钉扫码授权，给数字员工建一个独立企业账号
2. **填配置**：`cp config/constants.sh config/constants.local.sh`，填群 ID、profile、免费模型
3. **托管上线**：用 launchd（macOS）或 systemd --user（Linux）托管 `monitor.sh`，开机自启 + 崩溃自愈

然后去群里发条消息——数字员工就回你了。调试期可以 `AGENT_REPLY_MODE=log`，回复只写日志不发群，验证无误再开真发。

答案是：几分钟，零成本，一个会写 prompt 的人就能交付。
